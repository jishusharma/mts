## Detailed Notes & Audit Observations

1. **HIGH Broadcast Architecture**:
   - Every high broadcast (`--prio high`) receives a unique `b-xxxxxx` identifier computed from a SHA-1 digest (`scripts/dev/mts_signal.py:1449`).
   - The broadcast is surfaced at every prompt and session startup via `action_block()` (`scripts/dev/mts_signal.py:763-787`) until acknowledged by the specific host.
   - The Claude `Stop` event hook (`stop_check()`, lines 1176-1201) blocks assistant termination if the response omits the broadcast ID or the literal prefix `"ACTION FOR THIS MACHINE"`.

2. **Acknowledgment & Expiration Lifecycle**:
   - An acknowledgment of `told` parks the reminder for `TOLD_TTL_H = 2` hours (`scripts/dev/mts_signal.py:94, 670`). If not confirmed `done` within 2 hours, `told_expired()` re-activates the broadcast with urgency tag `"TOLD n h AGO, NOT DONE"` and restores the `Stop` block.
   - Commands (`--cmd`) strictly enforce non-empty `--note` describing the blocker when acking `told` (`scripts/dev/mts_signal.py:1520-1523`).
   - Stale broadcasts older than `STALE_H = 48` hours on inactive targets (silent >= 24 hours) are transitioned to `expired` by `expire` (`scripts/dev/mts_signal.py:697-708, 1544-1556`).

3. **Asks Subsystem**:
   - Asks receive a `q-xxxxxx` identifier with type-dependent wait and deadline windows (`ASK_TYPES`: ask=15/60m, resend=15/30m, task=30/240m; `scripts/dev/mts_signal.py:828`).
   - Duplicate asks sent to the same target within the minimum wait window are rejected/collapsed (`scripts/dev/mts_signal.py:990-994`).
   - When an ask passes its deadline unanswered, `escalate()` issues an escalation record (`kind="esc"`) to the target login's supervisor host parsed from recent `BUDGET sup=` telemetry (`scripts/dev/mts_signal.py:877-909`).

4. **NOT_IN_DATA Classification**:
   - In Clause 5, the claim `"for hosts that run no Claude session (the live Lenovo): mts_doctor.py BROADCAST warns on it"` accurately describes an external integration in `scripts/dev/mts_doctor.py`, but within the scope of `scripts/dev/mts_signal.py` and `scripts/dev/test_mts_signal.py`, no code or test implements or asserts this `mts_doctor.py` warning. Thus, it is classified as `NOT_IN_DATA` under the single-module code audit boundary.
