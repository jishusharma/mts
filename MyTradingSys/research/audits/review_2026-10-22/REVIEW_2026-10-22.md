**F1. The Supervisor is told the wrong first action (reproducible now).**

Re-run: the loop in this report's section 6, command C1.

**F2. The role file contradicts itself.** `supervisor.md` line 3 says "Read first" four files (about 46 KB). Line 4 says boot reads only what Boot step 3 names. A model cannot obey both. Supervisor boot is about 87k (72k harness + about 15k docs) before its first action.

**F3. Rules fight the app.** The Claude desktop app's own session-spawn instructions tell the model to offer or propose task cards (`offer`, `own_initiative`). MTS bans them and a hook denies them. Models are caught between two authorities, and on "event turns" the app refuses `start_session` entirely, so the rule set needs a fallback (Agents), which needs a third rule set (WORKERS.md rule 3).

**F4. Every layer re-pays a cold start.** Your WORKERS.md: an Agent starts at about 52k context, a session at about 73k, "4-5 turns of cost". The Supervisor chain is Supervisor, then Session_Planner Agent, then workers, then a review Agent, then a verification Haiku Agent. Five hops mean five cold starts before any value.

**F5. Rules that change daily cannot be followed.** Edits in the last 7 days: CLAUDE.md 30, roles 63, SUPER_SESSION.md 61, role_loader 12, turn_meter 11, mts_signal 9, supervisor.py 8, model_guard 7. Each edit risks a CI-size/lint failure; 124 commits matched retoken, red-CI or lint repairs.

**F6. The stale-checkout trap is still there.** `F:\MTS\repo` is a non-git Oct 6 snapshot. Your 10-18 audit measured 8.7 turns and about 215k cache-read tokens wasted per builder probing for `sync.py` (it proposed a fix; the folder is still present). I landed in it myself today.

**F7. Hooks.** Per tool call: PreToolUse turn_meter; PostToolUse turn_meter + mts_signal; per prompt: 5 hooks. Measured once on this desktop: shot 0.34 s, turn_meter 0.23 s, c_drive_guard 0.23 s, role_loader 0.28 s, stop_guard 0.32 s, **mts_signal 1.5 s and ci_watch 1.8 s** (both do network git or GitHub calls). Bare Python is 0.05 to 0.12 s. This is a modest wall-clock tax (about 0.5 s per tool call typically), but it is also 3 to 6 Python processes per call under Defender, which fits the CPU findings. It is a secondary cause, not the main one.

## 4. MTS broadcast: cost and verdict

- API token cost: effectively nil. At most 5 lines (about 100 to 150 tokens) appended to a turn, only when something new exists.
- Machine cost: one `git fetch` of the public `mts-signals` branch per machine every 5 min; one detached `git push` per send.
- What it cannot do: wake an idle session (its own docstring says "nothing wakes an idle session"), or cross logins (the app does not allow it). That is the capability you actually wanted.
- Recommendation: stop running it on PostToolUse and per prompt. Keep SessionStart only (one line at start) and the CLI `send/read`. For same-login awareness use the app's `list_sessions` and `send_message`. For cross-login awareness use STATUS.md plus the `claims` branch, which already exists.
