# Six slots: how to keep them busy (Thinker, 2026-10-22, decided 2026-10-23 IST)

Question (operator, 2026-10-22): "How can we utilize all 6 slots? ... constant communication between all our logins ... polling."
Answer (operator, 2026-10-23): "go with A + C - do it here". Record: OPERATOR_DECISIONS.md `d-six-slots-poll`.

## Facts (repo, read 2026-10-22)
- 6 slots = 3 machines x `GATE_SLOTS = 2` (scripts/dev/sync.py:143). A slot is held only while a ship gate runs: ~60 s fast, 544 s full
  (GATE_SPEED.md:34, :46).
- A worker runs 21-28 turns (WORKERS.md:7-8). Wall time per worker: NOT_IN_DATA (assumed ~30 min, OURS). So 2 busy gates per machine
  would need 7-60 workers per machine. Gates are spare capacity, not the bottleneck.
- The real limits:
  1. A machine with no live Supervisor gets 0 workers. Nothing can start a session on another machine (SCHEDULING_POLICY.md; only
     nuc_wake.py, SUPER_LOOP.md:30).
  2. Budget: A THROTTLE 97% of week, B THROTTLE 73% vs pace 64%, C SPEND 12% (`traffic.py budget`, 2026-10-22).
  3. Red CI blocks spawns.
  4. `RAMP = 1` (supervisor.py) plus a watcher that wakes only on a change, up to 50 min apart. A free slot with a ready card is not a
     change, so a Supervisor grew by one worker per 50 min.
- The queue was not empty: 19 ready SONNET cards and 1 ready HAIKU card.

## Cost of polling (per machine, per hour)
| Poller | Model tokens | GitHub REST | git fetch |
|---|---|---|---|
| Shell watcher every 300 s (`supervisor.py wait`) | 0 | 12 (`ci_watch` 1 call/probe) | 12 |
| Model poll every 5 min (option B) | ~540k eq | 12 | 12 |
| Actionable wake only (option A) | ~45k eq per wake, ~3 wakes max per ramp | same as shell | same |
3 machines x 12 = 36 REST calls/h = 0.7% of the 5,000/h limit.

## Options
- A (chosen): actionable wake. `wait --login L` also exits when the last plan left worker slots and ready cards unused, CI is green
  and a gate on this machine is free. When every gate is idle the ramp lifts from 1 to `slots`. Fail closed on unknown CI or gates;
  stops after 2 plans in a row that spawned nothing (`STUCK_MAX`, OURS).
- B: model poll every 5 min. Simple, but ~540k eq/h per Supervisor for mostly "nothing changed".
- C (chosen): revive idle machines. The shared-lane owner prints one line,
  `OPERATOR start a Supervisor on <host>`, when a machine has no heartbeat for 75 min, ready cards it can run and a login with fresh,
  non-THROTTLE budget and no live Supervisor. No auto-start (no schedulers).
- D: do nothing.

## New vs existing
- Existing patterns: lease/claim with expiry (our claims; Tandem MCP, taskops), heartbeat membership, merge queue (gate slots as a
  semaphore), and "cheap deterministic check before an expensive model call" (common advice for idle agents).
- New here: (1) the worker pool cannot start itself on another machine, so the last step is a human line; (2) capacity is a token
  budget window, not CPUs; (3) polling by the model costs money while polling by shell is free, so the shell decides when to wake.
