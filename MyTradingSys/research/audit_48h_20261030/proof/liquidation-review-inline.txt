# Review: liquidation accumulator shutdown drain

**Verdict:** I found no blocking or high-severity defects. The core change is sound: the `shuttingDown` check and the `offer` are atomic under the monitor, so no line is accepted after the flag is set. I found some medium and low issues, mostly around reporting and tests. Line numbers are approximate. I derived them from the diff hunks, so confirm them in the live file.

## Findings

| # | Sev | Location | Finding |
|---|---|---|---|
| 1 | Medium | `shutdown()`, ~L233 and ~L245, via `logErr` | **Loss reporting can be swallowed.** `logErr` is rate-limited to one message per 60 s and shares one timestamp. In the stalled-writer case, `"shutdown drain timed out"` prints and sets `lastLogErrPrint`. The `"shutdown dropped N queued events"` message that follows is then suppressed. Any earlier `write failed` message within 60 s has the same effect. Shutdown data loss can end up with no log line, only a counter that nothing reads at exit. Print the shutdown-loss message unconditionally, because it prints at most once. |
| 2 | Medium (test gap) | `shutdownDrainsAcceptedEventsBeforeReturning`, ~L96-105 | **The test does not reliably exercise the drain.** It passes whenever the writer outpaces 200 small appends. It does not prove that the drain wait is what makes it pass. It also cannot catch a regression where the drain is removed and the writer happens to keep up. Make the writer slow or gated, for example by using a package-private hook, or enqueue more events. Also assert that `shutdown()` returns within the bound. |
| 3 | Medium (test gap) | whole test file | **Several new paths have no coverage:** <br>• The drain-timeout path with a stalled writer, which also covers the in-flight line. <br>• `onMessage` after `shutdown()` increments `logDropped`, writes no line, and still updates the buckets. <br>• Concurrent `onMessage` and `shutdown()`, where accepted plus dropped should equal sent. <br>• `awaitLogIdle` returning true after an abandoned drain. `shutdownCountsAbandonedQueueWhenNoWriterExists` only asserts `logDropped`. It never checks that `logDone` was credited. |
| 4 | Low–Medium | `shutdown()`, ~L237 | **The in-flight line is lost on timeout.** If the drain times out while the writer is inside `Files.write`, the interrupt gives `ClosedByInterruptException`. That line is counted in `logErrors`, not `logDropped`, and is never retried. This is bounded and arguably acceptable, but the two counters are inconsistent for the same kind of loss. Document it or count it consistently. |
| 5 | Low | `shutdown()`, ~L224-227 | **A second or concurrent `shutdown()` returns before the first drain finishes.** A caller on that path may assume all events are flushed when they are not. The test only covers sequential calls. Document this, or make later callers wait. |
| 6 | Low | `shutdown()`, ~L226-229 | **Frames still arriving during `close()` are dropped.** The flag is set before `close()`, and `close()` is asynchronous. Frames received during the close handshake are counted as dropped and not logged. H3 has no REST backfill, so closing first and then flagging may lose less. This may be intentional, and the diff does not say. |
| 7 | Low | `shutdown()`, ~L228-229 | **A reconnect can race with shutdown.** `shutdownNow()` interrupts a task that may be inside `reconnectBlocking()`. `close()` can then run before the connection finishes opening, which leaves a live socket after shutdown. The socket would only drop log lines, but it leaks. This predates the change, though the change touches this code. |
| 8 | Low | `enqueueLog`, ~L76 | **The lock is on the public object, `this`.** It is `synchronized` on a `WebSocketClient` that external code can also lock. `logErr` and `System.err.println` also run while holding the lock. A stalled stderr could block the WS reader thread and `shutdown()`'s flag-set block. Use a private lock object and print outside the lock. |
| 9 | Low | `shutdown()`, ~L233 | **Shutdown time scales with the symbol count.** The drain wait is up to 5 s per instance. If callers shut down many symbols sequentially, the worst case is N × 5 s. Confirm the caller can afford that. |
| 10 | Nit | test file, ~L95 and end of file | There is no blank line before the new `@Test`, and a stray blank line sits before the closing brace. |

## Checked and fine
- `logEnqueued` is incremented under the same lock as the `offer`, and `shutdown()` takes that lock to set the flag. After the flag is set, the counters are consistent, so `awaitLogIdle` cannot return early on a counter race.
- The `poll` drain and the writer's `take` cannot both get the same element, so there is no double-count. The abandoned count is credited to `logDone`, so `awaitLogIdle` stays consistent afterwards.
- `awaitLogIdle` returns true only after `logDone` increments, which happens in `finally` after the write. Interrupting the writer after a successful drain only hits a blocked `take`.
- The interrupt handling in `shutdown()` correctly restores the thread's interrupt flag and still interrupts the writer in `finally`.
