## How work gets in and out
- Ask: `python scripts/dev/codex_run.py ask "<what you want checked or run>" --kind audit --scope <repo path>` writes a ready card
  (steps, scope_out and done_when come from the kind's template); commit and `sync.py ship`. Any Claude session does this for an Inbox item.
  In the Codex app (project folder `F:\MTS\mts-codex`) the operator can type the ask directly; Codex writes the card the same way, then works it.
- Run: (RETIRED 2026-10-17, see SCHEDULING_POLICY.md: MTS-CodexLab is unregistered; the coordinator runs `codex_run.py tick` on every wake) formerly Windows task `MTS-CodexLab` on JIS-NUC ran `codex_run.py tick` (refresh `F:\MTS\mts-codex-lab` on branch `jis-nuc/codex-lab`,
  take the first ready unclaimed CODEX card, claim it, start `codex exec` with the card's model and effort, then commit, ship and
  release). No card = no Codex call, no cost. One run at a time (lock). A card that fails twice without ending `done` is STUCK
  and skipped until someone looks (`codex_run.py status`). A run that ends INCOMPLETE or OUT_OF_SCOPE leaves its files in the lab
  work tree and the next tick stays IDLE until a session has looked at them: nothing half-done is shipped or thrown away.
- Deliver: one report per card in `research/layer_lab/reports/<UTC date>_<card>.md`, the card's `result` line, and
  `research/layer_lab/INDEX.md` (newest first, regenerated by `codex_run.py index`). `sync.py news` shows the commit.
- Pause: `codex_run.py stop "<why>"`, `resume`. Run log and per-run output: `%CODEX_HOME%\lab_runs\`.
- `tasks.py next` without `--lane` hides CODEX cards, so Claude relay sessions never take them; the claim is still the lock. Codex takes lane CODEX only (HAIKU/SONNET cards are for Claude relay sessions, run-and-report lanes for DSA).

## Report format
1. Verdict line: `SOUND` / `FIX-FIRST` / `BLOCKED` (audit), or the headline numbers (run), or changed files + test output (build).
2. What was checked or run: files with line ranges, commands, data range.
3. Findings table: severity HIGH/MED/LOW, file:line, what is wrong, evidence (quote or number), proposed fix. Every claim is
   MATCH / MISMATCH / NOT_IN_DATA against a file that was read; nothing from memory.
4. Follow-up cards created (ids).

## Allowance (Codex plan Plus: a 5-hour window and a weekly cap, shared with the operator's own app sessions)
- Nothing but the scheduled script feeds Codex: no Claude session, no Haiku worker. A ready CODEX card is the only input.
- Each tick reads the last allowance reading Codex wrote (`%CODEX_HOME%\sessions`). At 85% of the 5-hour window, or 85% of the
  week, the tick stays IDLE and the card waits for the reset (`codex_run.py status` prints both numbers). The last 15% of the
  week is the operator's.
- A run cut off by the allowance ends LIMIT: nothing shipped, the card stays ready, no try is charged.
- The allowance error in the log tail makes a run LIMIT even when Codex left partial files: they are moved (never deleted) to
  `%CODEX_HOME%\lab_runs\salvage\<stamp>_<card>\` so the lab tree is clean and the next tick is not blocked.
- Failover (2026-10-12): the first allowance/credit error marks the whole GPT lane down and `lane_health.py` moves or pauses cards (section below).
  Astra / high effort burns the shared allowance fastest (383k tokens in one audit): the operator's own app sessions on it
  are what starve the lab.
- Spend guard (2026-10-13; `codex_run.py`): the 85% pre-check only sees what is already used, so it cannot stop a card that starts at
  16% and moves the window 80 points. Each run is estimated (measured max of the setting's latest runs, else the table
  `EST_WINDOW_PTS`) and starts only if it fits under 100 minus a 10-point reserve, the lab's own spend stays under `LAB_WINDOW_PTS`
  (50) of the window and `LAB_WEEK_PTS` (60; 35 until 2026-10-16) of the week, at most `LAB_RUNS_PER_WINDOW` (10; 4 until 2026-10-16) runs and 1 astra run per window, one
  card per tick with `MIN_GAP_S` (20 min) between starts, and a card that ended INCOMPLETE waits `COOLDOWN_S` (2 h). When it is
  spent the tick prints `IDLE lab budget: ...` and waits for the reset; it does not mark the lane down or reroute cards. A cheaper
  card behind a held one still runs. `codex_run.py run <card> --force` is the operator's way past it.
- The run lock (`lab_runs/lab.lock`) is created exclusively and is taken over at once when its process no longer runs.
- Every run row in `runs.jsonl` carries the model and effort the CLI printed (`model_used`, `effort_used`), the session id, true
  tokens from the rollout file (`tokens_total` counts cached input; the CLI's own `tokens used` line, kept as `tokens`, leaves it
  out and under-reports about 10x) and the points the 5-hour window and the week moved (`window_pts`, `week_pts`; an operator app
  session running at the same time is included). `MyTradingSys/system/codex_usage.json` ships with each run and is what the
  Control Room "Claude-GPT cycle" section shows.
- Measured 2026-10-12 (JIS-NUC): sol/medium 0.7 to 1.7M tokens = 5 to 9 window points, 1 week point; astra/high 3.7 to 5.1M tokens =
  81 to 90 window points, 13 to 14 week points per run.
- Measured 2026-10-11: one high-effort audit = 200k tokens, 9 minutes. Keep the queue 4 to 8 cards deep; an empty queue wastes windows.
- Filling the queue is refinement work: any session turns a scoped card into lane CODEX (`kind`, `tests` or `commands`,
  scope_in) and ships it. Cards that touch the live path, shared engine files or a holdout never go to the lab.

## Guards

(measured 2026-10-11: a fetch from inside the sandbox is refused). So Codex never claims, commits or pushes: `codex_run.py` does

## GPT lane health, reroute and pause (operator 2026-10-12)
Why: the Astra audit hit "You've hit your usage limit ... purchase more credits or try again at ..." after 777 s of work (runs.jsonl 17:00Z); the earlier
gpt-6.1-sol runs printed the same line after 5 s and were retried every 30 min. Nothing moved the cards, so they just waited.
Code: `scripts/dev/lane_health.py` (rules at the top of the file), state `MyTradingSys/system/lane_state.json`, tests `test_lane_health.py` (gate step 3lh).
- **Down** at once on that error text in a run log (the last 4000 characters only), after 3 empty runs in a row, or when the lab host's heartbeat is older than **3 hours** (6 missed ticks). The state shows the ERROR line, including GPT's own reset time.
- **Window spent** (2026-10-12): when the pre-check refuses a card because the 5-hour window (>= 85%) or the week is used up, `codex_run.py` marks the lane down with reason `window` and `until` = the reset time, and the same tick runs the sweep, so ready CODEX cards move to DSA/Claude at once. No probe (it would only hit the limit); the lane comes back up by itself at the reset and untaken rows are cancelled.
- **Probe**: a down lane lets one card try every **60 min** (a crucial card first). DONE or BLOCKED = lane up again. A limit run costs 5 s and no try.
- **Reroute** (lane down): a ready CODEX card goes to DSA (kinds `audit`, `run`: a desk row whose prompt is cut from the card in the DSA bridge format: worktree mts-dsa, exact commands, one report path, stop-after-two-failures)
  or to lane SONNET (kind `build`: needs a test, a relay session takes it). The card keeps a `reroute` field saying where it went and why.
- **Pause**: a card flagged `crucial` or `gpt_only` (default off; `tasks.py flag <id> crucial`, or `tasks.py new ... --crucial`) is never moved. It waits, with the reason on the Control Room.
- **Resume** (lane up): an untaken DSA row is cancelled and the card is back on CODEX; an unclaimed SONNET card goes back to CODEX; work already taken stays. A finished DSA row closes its card with `via DSA (row): result`. Paused cards run again by themselves.
- **Who runs it** (RETIRED 2026-10-17, see SCHEDULING_POLICY.md: no timers; the coordinator runs both on wake): `codex_run.py tick` (JIS-NUC, was every 30 min, no model) and the Haiku watchdog `mts-lane-watch` (was hourly; catches a NUC that is off; prompt in `scripts/sched/relay_prompts/mts-lane-watch.SKILL.md`; not registered on JIS-NB as of 2026-10-15, register it where the NUC is watched). Operator override: `lane_health.py down "<why>"` / `up "<why>"`, then `sweep --apply --ship`.
- **See it**: Control Room, "Claude-GPT cycle", top box; `python scripts/dev/lane_health.py status`.
